# 群聊消息已读设计与改动范围

## 1. 方案决策

采用 **会话阅读游标 + 按消息作者定向推送 + 飞书比例圆圈**。
Server 保存每名成员的最高已读 `read_seq`，SDK 缓存成员游标并计算自己消息的已读人数和名单。
选择游标是为了复用现有 `read_seq` 和“读到这里，之前都算已读”的语义，减少连续阅读的载荷与状态维护。

- 阅读者上报 `conversationID + readSeq`。
- 部分阅读最多延迟 3 秒合并，读到末尾或显式刷新立即提交；Server 校验身份并通过现有读游标存储保证游标单调递增。
- Server 根据本次跨过的有效消息确定受影响作者，每名作者收到一条 `conversationID + userID + readSeq` 回执，其中 `userID` 是推进游标的阅读者。
- 定向范围是 `(oldReadSeq, newReadSeq]` 与最近 7 天消息的交集，查询作者后去重并排除阅读者本人和已退出群的作者；
  仅投递到这些作者的在线端。同一作者的多条消息合并为一条回执，离线端上线后同步校准。
- 登录和重连时，SDK 使用通用 `/msg/sync_conversation_read_states` 分批提交所有会话 ID，
  Server 返回各会话功能状态与参与者游标；成员变化时通过同一接口校准对应会话，之后用实时回执增量更新。
- 圆圈、悬浮摘要和已读/未读名单使用同一份游标缓存，在本地计算。

阅读上报与请求合并参考 Telegram；带阅读者 ID 的定向回执与批量同步是满足飞书式展示的项目适配。

## 2. 展示与统计口径

首版展示当前群人数不超过 **50 人**时，自己发送成功的普通群消息已读状态，覆盖任意年龄消息。
**7 天只限制实时推送的作者查询窗口**。这两个边界直接使用代码常量：

```go
const (
    GroupReadReceiptWindow     = 7 * 24 * time.Hour
    GroupReadReceiptMaxMembers = 50
)
```

人数限制与常量由 Server 统一控制，SDK/Web 根据响应的功能状态控制展示。超过 50 人的群仍正常更新自己的
`read_seq` 和未读计数，但跳过作者查询、群回执推送及成员游标同步。
超过 7 天的消息仍展示缓存计算的已读状态；同步最新成员游标后可恢复其人数和名单。

- 消息时间旁显示固定尺寸比例圆圈，无人已读为空环，全部已读为完成态。
- 悬浮显示少量已读姓名，或“X 人已读，Y 人未读”；点击显示头像、昵称及已读/未读双栏名单。
- 统计当前群成员并排除作者；成员进出后重新同步校准。
- 作者查看自己消息的已读人数和名单，成员信息包括头像和昵称。

```text
已读成员 = 当前成员中，除作者外 read_seq >= message.seq 的成员
未读成员 = 当前成员中，除作者外的其余成员
圆环比例 = 已读人数 / (当前群人数 - 1)，分母为 0 时显示空环
```

## 3. 同步与接口

- **登录与重连**：接入 SDK 现有同步流程，客户端按所有会话 ID 分批查询，包括未打开的群聊；
  单聊返回双方游标，通知会话返回自己的游标，群聊返回当前成员游标，使用同一种响应结构和 SDK 缓存。
  Server 校验成员资格和当前人数，并按会话返回结果：可用群返回 `enabled=true` 与成员 ID、游标；
  超过 50 人返回 `enabled=false`、`reason=MEMBER_LIMIT_EXCEEDED`，省略成员游标且跳过游标读取。
  超限是单个群的功能状态，其余群仍正常返回；客户端查询范围由已加入群决定。
  姓名、头像复用群成员资料缓存；点进会话直接使用已同步数据。
  同步结果覆盖任意年龄消息的已读计算，历史拉取的旧消息也直接与成员游标比较。
- **实时回执**：SDK 按 `(conversationID, userID)` 取最大游标，对重复和乱序事件去重；
  通知 Web 更新受影响的作者消息及已打开浮层，派生计算覆盖任意年龄消息。
  若阅读者只跨过 7 天前的消息，作者在下一次游标同步时校准旧消息状态。
- **成员变化与同步竞态**：成员变化后校准对应群的成员集合和游标；同步期间收到的增量按当前成员合并，
  避免旧响应覆盖更大的游标或保留已退出成员。
- **功能状态变化**：人数阈值按 Server 当前人数直接判定。超限时暂停圆圈和名单展示，保留缓存并标记待校准；
  恢复可用后同步最新成员游标，完成后恢复展示。连续成员变化合并同步，同一群最多一个在途同步请求，
  在途期间发生变化则完成后继续校准；退出群聊时清理缓存。
- **长期离线**：离线 100 天后上线，批量同步当前成员游标；
  随后标为全部已读时，作者查询仅覆盖游标区间内最近 7 天的消息。
- **未完成同步或同步失败**：已有成功同步的缓存时继续展示上次结果，成功后更新比例和名单；首次没有缓存时暂不展示。
  同步状态在内部处理，确认超限或退出群后隐藏。尚未确认的新成员游标先缓冲，完整同步确认成员关系后再参与统计。
- **权威数据**：成员关系与 Server 的 `read_seq` 是事实来源，消息计数和名单在 SDK 本地派生。
- **单聊统一**：单聊也原子推进 `read_seq`，回执只携带 `conversationID + userID + hasReadSeq`，定向发送给对方并同步阅读者其他端。
  登录、重连通过通用会话游标同步取得双方位置；消息 `isRead` 根据接收者游标派生，历史拉取和实时展示使用同一口径。
  Server 不逐条写入消息 `is_read`，SDK 普通消息也不逐条写入；阅后即焚的阅读时间仍在 SDK 本地保存。
  `OnRecvC2CReadReceipt` 改为游标事件，Core、WASM、JS 与 Web 同步更新。
- **阅读上报**：继续使用现有 `markConversationMessageAsRead` 表达读到末尾；
  单聊、群聊共同使用 `markConversationMessageAsReadBySeq({conversationID, seq, immediate})` 上报最高可见位置，
  共用 3 秒合并、立即提交和失败重试。读到末尾的入口取末尾 `seq` 后立即调用同一链路。
- **标记时机**：实际阅读或主动“标为已读”时推进游标，触发作者侧回执。
- **群已读接口与事件**：服务端回执包含 `conversationID + userID + readSeq`，同步结果包含逐群功能状态与成员游标。
  SDK 展示数据可复用 `GroupHasReadInfo`；作者侧消息计数变化可沿用 `OnRecvGroupReadReceipt` 的事件契约，
  由新游标处理链派生其数据。服务端游标回执与 SDK 消息展示事件分别定义。
- **复用与清理原则**：语义和契约适合的 API 继续使用，需要调整的同步修改 Core、WASM、JS 和 Web；
  实现时核对调用方，清理被新链路替代的逐消息上报、冗余查询和专用残留代码。

## 4. 改动范围

| 仓库                 | 必要改动                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------- |
| `abd-im-protocol`    | 带阅读者 ID 的游标回执、支持多会话且返回逐群功能状态的成员游标同步 RPC                            |
| `abd-im-server`      | 固定 7 天/50 人常量、限定时间窗口查找作者并定向推送、成员游标批量读取与校验                       |
| `abd-im-sdk-core`    | 阅读上报合并、登录/重连查询所有已加入群、功能状态及游标缓存、消息计数派生、事件接入与冗余代码清理 |
| `abd-im-sdk-js-wasm` | 接通游标同步与展示事件、补齐 WASM 注册和类型声明、复用适合的契约并清理被替代的 API                |
| `abd-im-web`         | 可见 seq 上报、圆圈与摘要、双栏名单、实时更新及同步状态                                           |

## 5. 性能与验收

阅读写入按成员游标进行，回执携带固定字段；一次上报给每名受影响作者最多一条通知。
Server 仍需查找游标跨过的近期消息作者，这部分读取成本必须计入压测。
存储查询限定会话、游标区间和发送时间窗口，利用支持范围定位的索引；
窗口内消息很多时分批读取作者所需字段并去重。
定向推送的投递量由受影响作者数决定。
首次或重连同步批量读取最多 50 名成员游标，使用 Redis pipeline / MongoDB 批量读取；
此上限按群计算，多群同步分批进行，压测同时覆盖大量已加入群的登录/重连同步。
SDK 每群缓存规模为成员数，人数与名单按消息在本地派生。

压测覆盖 10、30、50 人同时阅读、7 天内大量消息及离线 100 天后标为全部已读，
观察上报与回执 QPS、作者查找耗时、同步耗时和 P95/P99。
验收包含合并上报、重复/乱序回执、登录/重连自动校准未打开群的游标、重连漏事件恢复、同步与增量竞态、成员变化、
仅有效作者收到回执且同作者多消息合并、上线不自动已读、主动标为已读触发回执、
本地名单与圆圈一致，以及单聊已读和群未读清零无回归。
边界验收包括仅跨过 7 天前消息时不查询其作者、不推送回执，但旧消息仍展示已读状态，重连同步后正确校准；
50/51 人群由 Server 返回可用/超限状态，混合批次中可用群正常返回，超限群跳过游标读取；
客户端按状态暂停或恢复展示，会话未读正常清除；反复 50/51 人变化时合并同步，恢复展示前完成校准。

## 6. 实现接入

- Server 同步入口为 `/msg/sync_conversation_read_states`，每批最多 100 个会话；单聊和群聊统一使用 `HasReadReceipt`（2200）发送非持久实时通知。SDK 初始化或重连时批量拉取最终游标，不补放离线期间的逐次变更。
- 阅读 Webhook 保持原有配置、回调类型、命令、字段与触发规则，单聊 `Seqs` 透传请求值；内部游标读写和端侧回执独立调整。
- SDK 增加 `markConversationMessageAsReadBySeq`、`getGroupMessageReadInfo` 和 `refreshConversationReadStates`；上报、同步和缓存由各类会话共用，群聊展示数据通过 `OnRecvGroupReadReceipt` 更新，局部更新带 `partial=true`。
- 发送者游标继续使用原有缓存更新与异步持久化；设置游标接口保持仅同步自己的行为。实际阅读与主动“标为已读”走游标回执处理，Web 以消息实际可见、页面可见且有焦点为阅读条件。
- 消息作者按 `conversationID` 和 `(oldReadSeq, newReadSeq]` 查询，复用打包消息已有的唯一 `doc_id` 索引，不新增群 ID 复合索引。消息异步持久化落后时，作者查询短暂重试。
- `SeqUser` 保留原有 `GetUserReadSeq` / `SetUserReadSeq` 行为，只新增批量 `GetReadSeqs`；同步接口按会话及成员集合批量读取 MongoDB 游标。
- 本地联调使用 `/home/me/code/go.work` 关联 Protocol、Server 和 SDK Core；Web 使用 `file:../abd-im-sdk-js-wasm`。修改 Core 后先重新编译 SDK 的 `assets/openIM.wasm`，再构建 JS SDK 并更新 Web 本地依赖。
