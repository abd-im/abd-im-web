# 桌面端自动更新实施计划

本方案复用 chat 现有版本管理和 `POST /application/latest_version`，以 `electron-updater` 的标准 generic provider 完成下载、校验和安装。Windows x64 使用 NSIS EXE；macOS arm64 使用 DMG 首装、ZIP 更新。

## 1. 目标与范围

| 平台    | 架构  | 首次安装    | 自动更新                                      |
| ------- | ----- | ----------- | --------------------------------------------- |
| Windows | x64   | NSIS `.exe` | `.exe`、`latest.yml` 及构建生成的辅助文件     |
| macOS   | arm64 | `.dmg`      | `.zip`、`latest-mac.yml` 及构建生成的辅助文件 |

普通更新后台下载，完成后提供低打扰的重启入口；真正退出时可以安装，隐藏到托盘不安装。保留现有应用身份、安装范围、用户配置和聊天数据。

本期不扩展 chat 的版本接口、数据库字段或索引，不引入独立发布/撤回状态、灰度系统或自定义差分算法。每个平台只有上述一种受支持架构；以后支持同平台多个架构时再扩展版本协议。

## 2. 现有能力与必要补充

chat 已有版本增删改查和最新版本查询，字段包括 `platform`、`version`、`url`、`text`、`latest`、`force`、`hot`。原查询按 `latest` 降序、记录 ID 降序选择一条记录，不使用请求中的当前版本比较大小，也不按 SemVer 排序。

客户端补充 SemVer 比较、目标平台校验和标准更新清单接入；构建流程补充签名、公证、清单及产物验证。现有后台继续录入版本信息，不增加另一套发布流程。

## 3. 整体方案

### 3.1 与常见更新方案的关系

`electron-updater` 官方支持通过 generic HTTP(S) 服务提供更新清单及安装包。业务接口选择候选版本，更新库从候选包所在目录读取标准清单，仍使用库提供的下载、哈希校验和原生安装能力。

业务版本管理不必采用 GitHub Releases，也不必新增专门的发布接口。复用现有版本查询属于业务适配，不改变标准更新机制。Linear 风格仅指本项目的低打扰交互，不表示复刻其内部更新技术。

### 3.2 数据流

1. 构建机生成目标平台的签名安装包、更新清单和辅助文件。
2. 发布机校验完整产物并上传至不可变版本目录。
3. 管理员确认准备发布后，通过原有版本表单新增记录。
4. 桌面主进程请求现有 `latest_version`，客户端判断是否为更高稳定版本。
5. 从安装包 URL 的父目录读取 `latest.yml` 或 `latest-mac.yml`。
6. 清单与候选版本、架构匹配后，由更新库下载和校验。
7. 保存草稿并确认没有活跃任务后，交给原生安装器。

## 4. 复用版本协议

### 4.1 请求与响应

接口仍为 chat API 的 `POST /application/latest_version`；部署时保留实际代理前缀，不改服务端响应结构。

请求：

```json
{ "platform": "mac", "version": "1.0.0" }
```

响应示例：

```json
{
  "errCode": 0,
  "data": {
    "version": {
      "id": "0123456789abcdef01234567",
      "platform": "mac",
      "version": "1.0.1",
      "url": "https://downloads.example.com/abd-im/mac/arm64/1.0.1/ABD-IM_1.0.1_arm64.dmg",
      "text": "修复通知显示问题",
      "force": false,
      "latest": true,
      "hot": false,
      "createTime": 1788800000000
    }
  }
}
```

`data.version` 为空表示没有候选记录。客户端只接受平台匹配、版本号规范且高于当前版本的稳定记录；`hot=true` 和预发布记录不进入自动更新。格式错误、非可信下载源或安装包目标不匹配会报告校验失败，不触发安装。

### 4.2 平台、清单和地址约定

- `windows` 固定对应 x64，安装包文件名以 `_x64.exe` 结尾。
- `mac` 固定对应 arm64，后台登记的首装包以 `_arm64.dmg` 结尾，清单必须包含同版本 `_arm64.zip`。
- 清单与安装包在同一不可变版本目录。客户端通过 URL API 取得父目录，不给后台增加 `feedUrl` 字段。
- 安装包和清单必须使用构建时允许列表内的 HTTPS origin，禁止凭据、查询参数或片段。
- 使用 electron-builder 的真实输出，不手写更新清单；文件名、版本、架构、SHA-512 和大小须一致。

### 4.3 发布与停止分发的边界

沿用 `add_version`、`update_version`、`delete_version` 和现有排序。创建记录就可能被查询选中，不存在草稿状态；`latest=false` 只是排序优先级，不能当作“未发布”。测试包只上传到隔离目录，不登记到正式版本列表。

新稳定版本通常设置 `latest=true`、`hot=false`、`force=false`。客户端只比较接口选中的一条记录，不会遍历历史寻找最高版本；管理员须确保选中的是预期版本。需要切换回已有记录时同时检查其他记录的优先标记。

删除错误记录或调整优先标记可以改变后续查询结果，但不保证终止正在下载或已经下载的候选包，也不会回滚已安装客户端。本期没有按发布 ID 远程撤回缓存包的能力。发现问题应发布更高版本修复，不能覆盖原版本目录。

原有客户端仍能使用同一安装包下载地址，无须新增兼容记录。尚未包含更新器的历史安装包需要先手动安装一次带更新器的版本。

## 5. 客户端实现

### 5.1 更新管理与 IPC

主进程以 `app.getVersion()`、`process.platform`、`process.arch` 为准。开发模式和非目标平台关闭真实更新。构建时注入 API 地址和下载 origin 允许列表，渲染进程不能指定任意 URL、安装路径或目标版本。

启动约 10 秒后检查，每 4 小时再次检查；系统恢复时按时间间隔补查，“关于”页提供手动检查。检查失败按 1 分钟起步、最多 15 分钟退避重试。

更新库设置 `autoDownload=false`，先验证候选记录及清单，再主动触发下载。普通用户不需要额外确认下载。禁止并发检查/下载；候选包校验完成后保留该候选，不再调用会替换它的检查流程。

```text
idle -> checking -> upToDate
                 -> downloading -> verifying -> downloaded -> installing
                 -> error
```

下载达到 100% 后仍等待库完成验证。主进程维护单一状态及 revision，渲染进程重载后通过快照恢复。IPC 校验主窗口和主 frame，暴露检查、状态、安装、退出、手动下载与退出准备结果等有限命令。

当前进程已有可信候选包时允许离线安装。进程重启后的缓存恢复由更新库重新校验，本期不提供自定义离线缓存安装入口。

### 5.2 Linear 风格交互规范

此处指低打扰、信息紧凑、动作明确的产品风格，不声称复刻 Linear 当前客户端或其内部更新技术。使用本项目现有 `src/styles/tokens.css` 和实际组件约定，归档设计文档只作风格背景，不覆盖当前样式。

#### 入口和布局

- 全局入口放在现有 60px 主导航底部，用 32px 图标按钮承载；就绪时配一个状态点，悬停 tooltip 为“重启以更新到 1.0.1”。导航宽度保持不变。
- 聊天侧栏原有 48px 品牌色更新横条移除；更新提示不再挤压会话列表，不只在聊天路由可见。
- 登录页在应用壳底部使用同一状态入口，不挤压登录表单；“关于”页提供固定的版本和检查更新行。
- Popover 使用 `width: 320px; max-width: calc(100vw - 24px)`，默认在入口右上方展开，由浮层定位组件处理边界。登录页详情按入口位置调整方向，不遮挡窗口控制按钮。
- 布局依次为图标与状态标题、版本号、按需显示的进度/说明、操作行。更新说明默认折叠，展开区域限制高度并滚动，不在 Popover 内再套卡片。
- 使用现有 Ant Design Popover/Dialog 的受控模式并匹配 token，不再增加一套组件库。Popover 关闭后焦点回到入口，Escape 只关闭详情，不能触发窗口最小化。

#### 状态与操作

| 状态             | 默认反馈                                   | 详情和可执行操作                                                     |
| ---------------- | ------------------------------------------ | -------------------------------------------------------------------- |
| 自动检查、无更新 | 不弹 toast、不自动展开、不抢焦点           | 关于页显示当前版本和最近检查时间                                     |
| 手动检查         | 仅当前入口显示加载状态，操作不可重复触发   | “正在检查更新”；无新版时显示“已是最新版本”                           |
| 后台下载         | 导航使用低对比下载图标，无大横条或弹窗     | “正在下载更新”、目标版本、真实百分比与细进度条；允许关闭详情继续工作 |
| 文件校验         | 无阻塞提示                                 | “正在准备更新”，不显示虚假百分比，不允许提前重启安装                 |
| 就绪             | 导航出现状态点，入口可发现；不自动打开详情 | “更新已就绪”、“重启更新”、次要“稍后”，以及“也会在退出应用时安装”     |
| 自动检查失败     | 保持安静并后台重试，不抢走已就绪状态       | 关于页显示“检查失败”与重试；不显示鉴权或实现细节                     |
| 下载失败         | 导航显示克制的失败状态，不循环弹 toast     | 简短原因和“重试下载”，手动下载安装作为次级回退                       |
| 安装准备中       | 已点击的安装操作进入稳定尺寸加载状态       | “正在重启”，禁用重复提交；失败恢复就绪或对应可重试状态               |

用户点击“重启更新”即表达安装意图，业务空闲时直接保存并安装，不再弹第二次“确定更新吗”。点击“稍后”只关闭详情，不删除已下载文件、不反复弹出提醒，就绪入口保留。

长更新说明按纯文本或既有安全 Markdown 渲染方式展示，禁止执行 HTML。面向用户只显示可理解的原因和恢复动作，不暴露 feed URL、哈希、堆栈或原始服务端错误；完整诊断写日志。

#### 视觉、动效和无障碍

- 背景使用 `--surface-raised`，分隔线使用 `--surface-border`，正文使用 `--foreground`，辅助信息使用 `--muted-foreground`；沿用亮暗主题，不新增更新专属配色系统。
- 正文 13px，辅助信息 12px，紧凑标题 14px，中等字重；字间距为 0，不使用大标题或随视口缩放的字号。
- 控件和浮层圆角 6-8px；图标使用现有 `lucide-react`，如 `Download`、`RefreshCw`、`CircleCheck`、`CircleAlert`，常规图标 16px。
- 主操作仅“重启更新”或当前恢复动作使用明确的填充按钮，其余为弱化按钮；避免整块品牌色背景、营销插画和重复通知。
- 进度条 2-3px，进度数字预留固定宽度；未知总量使用不定进度。动画控制在 120-160ms 并响应 `prefers-reduced-motion`，状态变化不使导航和按钮跳动。
- 图标按钮具备可访问名称和键盘焦点；进度使用可访问进度语义，仅在阶段变化时以 `aria-live="polite"` 播报，避免每个百分比都打断读屏。
- 强制更新对话框使用 focus trap，提供可访问的退出操作；关闭图标或 Escape 不允许绕过业务限制，但详情浮层不应捕获应用所有快捷键。

### 5.3 强制更新与退出保护

- 沿用候选记录的 `force`；后续版本须明确设置，不自动继承旧版本策略。
- 强制更新只作为客户端产品策略，显示原因、下载进度、重试、退出及手动下载入口；不等于服务端封禁旧客户端。
- 网络失败本身不构成强制更新依据。
- 文本发送、附件读取/转码/发送、上传和通话期间不直接安装；提示忙碌并等待用户稍后重试。
- 两个安装入口都先保存草稿和设置，短暂阻止新任务；保存失败或渲染进程 5 秒内无响应时恢复使用，不强行重启。
- 草稿按用户和会话保存正文，不持久化引用上下文或尚未提交的文件选择。
- `autoInstallOnAppQuit=false`，统一退出流程准备成功后调用 `quitAndInstall(true, restart)`。点击重启时重新打开，真正退出时保持退出。
- 托盘隐藏、最小化和关闭详情不安装；崩溃、强制终止、系统关机不承诺安装成功。

## 6. 构建与产物托管

Windows 保持 NSIS、现有 appId 和每机安装范围，允许未签名测试构建，正式分发建议签名；可能出现 UAC。macOS 使用 Developer ID 签名及 Apple 公证，生成 DMG 和 ZIP，正式构建不使用 ad-hoc 兜底。

```text
/downloads/abd-im/windows/x64/1.0.1/
  latest.yml
  ABD-IM_1.0.1_x64.exe
  <构建生成的辅助文件>
/downloads/abd-im/mac/arm64/1.0.1/
  latest-mac.yml
  ABD-IM_1.0.1_arm64.dmg
  ABD-IM_1.0.1_arm64.zip
  <构建生成的辅助文件>
```

目录名、文件名以真实构建输出为准。上传前校验 SHA-512 和大小，上传至临时目录后原子就位，拒绝覆盖同版本目录。上传脚本不调用业务发布接口；正式登记由原有管理页面完成。

CI 仅允许手动触发，运行检查、签名构建并保存 workflow artifacts，不自动创建 GitHub Release、不上传站点、不登记业务版本。

清单使用 `no-cache`，安装包可长期缓存。托管站点验证 HTTPS、HTTP 200、Range 206、Content-Length 和缺失文件 404，禁止将缺失清单回退为 SPA HTML。

| 仓库             | 改动                                                                                                         |

| abd-im-web       | 主进程更新管理、旧接口适配、generic 清单校验、IPC、Linear 风格入口、草稿和任务保护、签名构建、上传及测试     |
| abd-im-admin-web | 复用原版本增删改页面；保留静态更新文件的 Nginx 配置和部署说明，不新增发布/撤回 API                           |

管理端 token 失效统一退出登录，不增加自动刷新接口。shadcn UI 重构属于独立工作，不纳入本次更新功能提交。

## 8. 实施顺序与验收

1. 对照原有版本协议完成客户端适配，覆盖空记录、同版本、旧版本、预发布、错误平台与下载源。
2. 生成两个目标平台的正式签名产物，校验清单与文件的一致性。
3. 在隔离下载目录及测试版本数据中验证查询、下载、错误重试、重启和退出保护。
4. 更新管理端说明，确认新增记录即可参与原查询，不能将 `latest=false` 当草稿。
5. 完成真实平台跨版本安装后，人工登记正式版本。

### 真实平台验收

分别从较低测试版本升级到较高版本，验证签名、公证、安装位置、退出不重开、重启会重开、登录/聊天/配置/草稿保留、托盘隐藏、通话及附件保护、离线候选包、包损坏、磁盘不足和权限错误。

Mac 从 Applications 运行，并验证从 DMG 运行及无写权限时的表现；Windows 验证 UAC 和原安装目录兼容。不能用浏览器模拟桥接测试代替这一步。

## 9. 测试与上线边界

自动化覆盖更新状态机、原接口数据适配、安装命令及退出保护、产物校验和浏览器更新交互。纯 Web 不启用原生更新。

Linux 环境尚未生成正式签名安装包或完成真实跨版本安装。客户端全量渲染层 TypeScript 仍有原有错误；Electron 主进程单独检查。不执行数据库迁移，不向生产站点上传测试包。
